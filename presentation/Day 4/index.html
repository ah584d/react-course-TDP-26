Prop drilling

The problem: Prop drilling

What is "prop drilling"?

// Layer 0 - State lives here
function App() {
  const [user, setUser] = useState({
    name: "John Doe",
    email: "john@example.com"
  });
  return <Dashboard user={user} />;
}

// Layer 1 - Doesn't use user, just passes it down ❌
function Dashboard({ user }) {
  return <Sidebar user={user} />;
}

// Layer 2 - Doesn't use user, just passes it down ❌
function Sidebar({ user }) {
  return <UserProfile user={user} />;
}

// Layer 3 - Finally uses it! ✅
function UserProfile({ user }) {
  return <div>{user.name} - {user.email}</div>;
}

👉 3 layers of drilling just to pass user from App to UserProfile

Why prop drilling is a problem

  • Maintenance burden: Every intermediate component must know about props it doesn't use
  • Tight coupling: Components become unnecessarily dependent on their parent's data structure
  • Refactoring nightmare: Adding or removing a prop requires changes across multiple files

Why prop drilling is a problem (cont.)

  • Reduced reusability: Components polluted with pass-through props are harder to reuse
  • Code noise: Props list grows, obscuring which data is actually used

Solution categories

  • Context API (built-in)
  • External state libraries (Zustand, Redux, etc.)

What is context?

👉 A way to share data globally without props

Best for:

  • Theme (dark/light)
  • Auth user
  • Language / locale

Context API - 3 steps

// 1️⃣ Create Context
const ThemeContext = createContext(null);

// 2️⃣ Provide value at the top level
function App() {
  const [theme, setTheme] = useState("dark");

  return (
    <ThemeContext.Provider value={theme}>
      <Header />
      <Content />
    </ThemeContext.Provider>
  );
}

// 3️⃣ Consume anywhere in the tree
function Header() {
  const theme = useContext(ThemeContext);
  return <header className={theme}>Current: {theme}</header>;
}
createContext Provider useContext

Sharing state + setter via Context

Pass both theme and setTheme so children can update

// Provider passes BOTH value and setter
function App() {
  const [theme, setTheme] = useState("dark");

  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      <Header />
      <Content />
    </ThemeContext.Provider>
  );
}

// Any child can now READ and UPDATE the theme
function Header() {
  const { theme, setTheme } = useContext(ThemeContext);

  const toggleTheme = () =>
    setTheme(prev => prev === "dark" ? "light" : "dark");

  return (
    <header className={theme}>
      <span>Current: {theme}</span>
      <button onClick={toggleTheme}>Toggle Theme</button>
    </header>
  );
}

Important concept

⚠️ Context is NOT a state manager

👉 It only shares values

👉 You still need useState or useReducer

Solution: Provider + custom hook

import { createContext, useContext, useState } from "react";

const ThemeContext = createContext(null);

export const ThemeProvider = ({ children }) => {
  const [theme, setTheme] = useState("light");

  const toggleTheme = () =>
    setTheme((prev) => (prev === "light" ? "dark" : "light"));

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext.Provider>
  );
};

// Custom hook for easy access
export const useTheme = () => {
  const context = useContext(ThemeContext);
  if (!context) {
    throw new Error("useTheme must be used within ThemeProvider");
  }
  return context;
};

Usage: consuming the context

// 1️⃣ Wrap your app once
<ThemeProvider>
  <App />
</ThemeProvider>
// 2️⃣ Any component inside can read AND update
const Button = () => {
  const { theme, toggleTheme } = useTheme();

  return (
    <button onClick={toggleTheme}>
      Current: {theme}
    </button>
  );
};
🧠 Teaching Notes
  • Custom hook (useTheme) is BEST PRACTICE
  • No prop drilling — Button calls toggleTheme directly
  • Re-renders happen when value changes

What is Zustand?

📦 What it provides:

  • Single source of truth
  • No providers needed
  • Simple API
  • TypeScript ready
  • Minimal boilerplate

✨ Why use it?

  • Less code than Context
  • Better performance
  • No wrapper hell
  • Easy to test
  • Works outside React

💡 Perfect for: Shopping carts, user data, global UI state

Context downside: Performance issue ⚠️

Large contexts cause unnecessary re-renders

Context performance — in code

// ❌ One big context with everything
const AppContext = createContext(null);

function AppProvider({ children }) {
  const [user, setUser] = useState({ name: "John", email: "john@ex.com" });
  const [theme, setTheme] = useState("dark");
  const [notifications, setNotifications] = useState(5);
  const [cart, setCart] = useState({ items: [] });

  return (
    <AppContext.Provider value={{ user, theme, notifications, cart,
                                   setUser, setTheme, setNotifications, setCart }}>
      {children}
    </AppContext.Provider>
  );
}

// Header only needs theme — but re-renders when notifications change!
function Header() {
  const { theme } = useContext(AppContext); // 🔄 re-renders on ANY change
  return <header className={theme}>...</header>;
}

// NotificationBell updates notifications → triggers Header + Cart re-render
function NotificationBell() {
  const { notifications, setNotifications } = useContext(AppContext);
  return (
    <button onClick={() => setNotifications(n => n + 1)}>
      🔔 {notifications}
    </button>
  );
}

⚠️ Clicking the bell → notifications changes → Header and Cart re-render even though they only use theme / cart

Why Zustand instead of Redux?

Redux is the most popular state management library

(used by millions of apps worldwide)

👉 So why learn Zustand instead?

Redux challenges

  • Steep learning curve: Many concepts to master before being productive
  • Lots of boilerplate: Multiple files and patterns for simple state updates
  • Complex structure: Actions, reducers, action types, constants...

Redux challenges (cont.)

  • Middleware required: Need extra setup (Redux Thunk/Saga) for async operations
  • Complex setup: Store configuration, provider wrapping, dev tools integration

Zustand advantages

  • Learn in 10 minutes: Simple API with minimal concepts to understand
  • Minimal boilerplate: Just define your store and use it - no extra files needed
  • Just one hook: Create store with `create()`, use it with the returned hook

Zustand advantages (cont.)

  • Async built-in: Handle async operations directly - no middleware needed
  • Setup in 5 lines: Define state and actions in one simple object

🎯 For this course: Zustand gives you 80% of Redux power with 20% of the complexity

Mental model: Store = State + Actions

A Zustand store is just a JavaScript object 

const store = {
  // State (data)
  count: 0,
  user: null,
  isLoading: false,

  // Actions (functions that change state)
  increment: () => { /* ... */ },
  setUser: (user) => { /* ... */ },
  toggleLoading: () => { /* ... */ }
}

✨ That's it! No reducers, no actions, no dispatch

Just plain JavaScript objects and functions

Zustand API: Just 2 things to learn

1️⃣ create() - Create a store
import { create } from 'zustand';

const useStore = create((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 }))
}));
2️⃣ useStore() - Use the store
function Counter() {
  const count = useStore((state) => state.count);
  const increment = useStore((state) => state.increment);

  return <button onClick={increment}>{count}</button>;
}

🎯 Compare to Redux: actions, reducers, dispatch, middleware, combineReducers, applyMiddleware...
