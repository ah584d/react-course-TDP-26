What is Next.js?

A React framework with built-in features for production

🎯 Core Philosophy

React gives you the tools → Next.js gives you the structure

React vs Next.js

React Alone:

  • UI library only
  • You configure routing
  • You handle (Search Engine Optimization)
  • You setup build tools
  • Client-side only

Next.js Adds:

  • Full framework
  • Built-in routing
  • SEO-friendly by default
  • Zero config needed
  • Server + Client rendering

Why Use Next.js?

  • ⚡ Performance: Server-side rendering, automatic code splitting, and image optimization for lightning-fast apps
  • 🔍 SEO: Pre-rendered pages, metadata API, and sitemap generation make your site search-engine friendly
  • 🛣️ Routing: File-based routing with built-in layouts, loading states, and error handling

Why Use Next.js? (continued)

  • 🔧 Full-Stack: API routes, server actions, and seamless database integration
  • 🔧 Deployment: Deploy anywhere - Vercel offers one-click deployment, but Next.js works on any Node.js hosting platform (AWS, Azure, Google Cloud, DigitalOcean, Netlify, or even your own server)

💡 A complete framework that handles routing, rendering, data fetching, and deployment

Next.js has two routing systems

📁 Pages Router

(Legacy - Still supported)

  • pages/ directory
  • Client components by default
  • getServerSideProps
  • getStaticProps

🆕 App Router

(Recommended since Next.js 13+)

  • app/ directory
  • Server components by default
  • Layouts & templates
  • Streaming & suspense
  • Better performance

💡 Default in Nextjs version 16 - App Router

How Params Travel: Server → Client

Understanding the request-response flow

🔄 The Flow

  1. Client (Browser) sends HTTP request to server with URL
  2. Server (Next.js) processes the request, extracts params, and generates HTML
  3. Server sends back fully rendered HTML page
  4. Client receives and displays the page

Dynamic Parameter Extraction

How Next.js extracts values from URLs

📂 File Structure 

app/
└── post/
    └── [slug]/
        └── page.tsx

The [slug] folder name tells Next.js:
"This segment is dynamic!"

🔍 URL Matching

URL: /post/hello-world
Pattern: /post/[slug]
Extracted: slug = "hello-world"

💡 How It Works 

// page.tsx receives params automatically
export default async function PostPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;  // "hello-world"

  // Use slug to fetch data, render content, etc.
  const post = await getPostBySlug(slug);
  return <article>{post.title}</article>;
}
⚠️ Important: Params Are Always Strings

Type conversion is needed for numbers

The Problem

URL segments are always extracted as strings. Even if your URL is /products/123, the param will be "123" (string), not 123 (number).

❌ Wrong 

const { id } = await params;
// id is "123" (string)

if (id > 100) {  // ⚠️ Comparing string!
  // Unexpected behavior
}

✅ Correct 

const { id: idString } = await params;
const id = parseInt(idString);
// id is 123 (number)

if (id > 100) {  // ✅ Comparing number
  // Works as expected
}

💡 Tip: Use parseInt() for integers, parseFloat() for decimals, or Number() for general conversion.

Root Layout

The top-level layout that wraps your entire app

📁 app/layout.tsx

The Root Layout is required in every Next.js app. It defines the outermost HTML structure that wraps all pages.

  • Must return <html> and <body> tags
  • Receives a children prop — this is where your page content renders
  • Applied to every page in your application
  • Perfect place for global navigation, footer, fonts, and analytics
  • Does not re-render when users navigate between pages

Layout Benefits

Why layouts are powerful in Next.js

💡 Common Use Cases

  • Global navigation bar
  • Footer
  • Analytics scripts
  • Global styles/fonts
  • Theme providers
  • Authentication wrappers

⚡ Performance Note

Because layouts don't re-render on navigation, your header/footer stay mounted, making page transitions instant and smooth.

💡 This means no "flash" when navigating between pages — the layout stays constant while only the page content changes.

How the browser gets your UI

What is Hydration? 💧

Making static HTML interactive

The Process

React "wakes up" server HTML by attaching events & state.

1️⃣ Server sends HTML

Server renders HTML. User sees content but can't interact yet.

2️⃣ React hydrates

React loads & attaches event handlers (onClick, etc.).

3️⃣ Fully interactive

Page becomes fully interactive. All features work.

⚡ Best of Both

Fast initial load + Full interactivity.

💡 React expects server & client HTML to match. Mismatches = hydration errors.

Client vs Server Rendering

Where does your component become <html>?

Client-Side Rendering (CSR)

  • Browser downloads a basic HTML shell (e.g., <div id="root"></div>) + JS.
  • React runs in browser, creating and mounting the UI dynamically.
  • Slower initial load, big JS bundle.
  • Used in traditional React (Vite).

Server-Side Rendering (SSR)

  • Server generates HTML.
  • Browser gets full HTML immediately.
  • React "hydrates" it to make it interactive.
  • Faster load, better SEO.

Mental Shift Model

Thinking in boundaries

The Network Boundary

Server (Back-end)
  • Keep secrets safe (API keys)
  • Direct DB Queries
  • No JS sent to browser
  • Default in Next.js
Client (Front-end)
  • Interactive (onClick)
  • State (useState)
  • Browser APIs (window, localStorage)
  • Requires 'use client'

The default in Next.js App Router

🖥️ Server Components

(default)

  • Render on server
  • Can access backend directly
  • No JavaScript to browser
  • Better performance
  • SEO-friendly

💻 Client Components

('use client')

  • Render in browser
  • Can use hooks (useState)
  • Can use event handlers
  • Interactive
  • Adds JavaScript bundle

💡 Use Server Components by default, Client only when needed!

Summary: CSR vs SSR

How rendering approaches compare

Feature CSR (Vite/React) SSR (Next.js)
Initial HTML Empty <div> Fully rendered
JS Bundle Size All components are sent to the browser Client components are sent for hydration
Initial Load (User) UI appears after JavaScript loads HTML is visible immediately
Hooks/Interactivity ✅ Yes ✅ Yes after hydration
Direct DB Access ❌ No — use an API or server ✅ Server-rendered code can access the database

💡 CSR: The browser renders the UI and provides interactivity.
SSR: The server sends the initial HTML, then client JavaScript can hydrate interactive parts.

When to Use Client Components

'use client';

import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>
        Increment
      </button>
    </div>
  );
}

Use Client when you need:

  • useState, useEffect, or other hooks
  • Event handlers (onClick, onChange)
  • Browser APIs (localStorage, window)
  • Third-party libraries that use hooks

Data Fetching in Server Components

Super simple - just async/await!

// app/posts/page.tsx - Server Component
async function getPosts() {
  const res = await fetch('https://api.example.com/posts');
  return res.json();
}

export default async function PostsPage() {
  const posts = await getPosts();

  return (
    <div>
      <h1>Blog Posts</h1>
      {posts.map((post) => (
        <article key={post.id}>
          <h2>{post.title}</h2>
          <p>{post.excerpt}</p>
        </article>
      ))}
    </div>
  );
}

✨ No useEffect, no loading state management - it's automatic!

Streaming Data with Suspense

Show UI immediately while data continues to load

React Suspense

Instead of waiting for all data to load before showing the page, you can stream parts of the UI as they become ready. 

import { Suspense } from 'react';
import { PostFeed } from './components';

export default function Home() {
  return (
    <main>
      <h1>Dashboard</h1>

      {/* Renders immediately, shows fallback while loading */}
      <Suspense fallback={<p>Loading generic feed...</p>}>
        <PostFeed />
      </Suspense>
    </main>
  );
}

// This async Server Component streams its content
export async function PostFeed() {
  const posts = await fetch('https://api.example.com/posts')
    .then((res) => res.json());

  return (
    <section>
      <h2>Latest Posts</h2>
      {posts.map((post) => (
        <article key={post.id}>{post.title}</article>
      ))}
    </section>
  );
}

Server Actions

Run secure server code directly from components

The idea

A Server Action is a server function that a form or button can call directly. Next.js sends the input to the server and runs the function there.

Why use it instead of REST?

  • Less code for mutations inside one Next.js app.
  • No separate API route, fetch call, or JSON plumbing.
  • Useful for forms that only this app needs to submit.

Use REST instead when other apps, mobile clients, or third-party consumers need the same API. Always validate input and check permissions in either approach.

Server Actions: Form Example

Submit a form directly to a server-side function 

export default function Form() {
  // This function runs on the SERVER!
  async function createPost(formData: FormData) {
    'use server'; // The magic directive ✨

    const title = formData.get('title');
    await db.post.create({ title }); // Direct DB mutation!
  }

  return (
    <form action={createPost}>
      <input type="text" name="title" />
      <button type="submit">Submit</button>
    </form>
  );
}

Reserved Filenames

Next.js automatically uses these files

In the App Router, files with specific names have special magical behavior. Next.js wraps your page.tsx with these automatically!

layout.tsx Wraps the page (and all children) in shared UI.
loading.tsx Shown AUTOMATICALLY while page.tsx is fetching data.
error.tsx Catches any errors inside the folder and shows fallback UI.

💡 You never import these files! Just create them, and Next.js handles the rest.

Next.js Best Practices

✅ DO

  • Use Server Components by default
  • Add metadata to all pages
  • Use next/image for images
  • Use next/link for navigation
  • Keep client components small
  • Use TypeScript

❌ DON'T

  • Use <a> tags for internal links
  • Fetch Component data in Client Components
  • Make everything 'use client'
  • Ignore loading states
  • Forget error handling

Next.js Summary

🌟 Core Concepts

  • App Router: Folder-based routing where only page.tsx is publicly accessible.
  • Rendering: RSCs (Server) are default for SEO/Performance. CSR (Client) is for interactivity.
  • Data Fetching: Fetch data on the Server using async/await directly in your components.
  • Params: Dynamic route params (e.g., [id]) are now Asynchronous and must be awaited.
  • Suspense/Streaming: Use loading.tsx (or Suspense directly) for instant UI while data loads.

🧠 Key Takeaways

  • Next.js is a React framework with built-in routing, SSR, and more
  • App Router uses file-based routing (folder = route)
  • Server Components are the default (fast & SEO-friendly)
  • Use 'use client' only when you need interactivity
  • Data fetching is simple with async/await
  • Built-in loading and error handling
  • Deploy to Vercel with one click

Static Rendering

Default behavior in Next.js

Static Rendering (SSG)

  • Pre-rendered at build time.
  • Incredibly fast (served from CDN).
  • Best for blog posts, marketing pages.

Dynamic Rendering

  • Rendered on-demand for each request.
  • Triggered automatically if you use cookies(), headers(), or URL searchParams.
  • Best for user dashboards, real-time data.

Rendering Strategies Overview

Next.js supports multiple rendering strategies

Strategy When Rendered Performance Use Case
SSG
Static Site Generation 		Build time ⚡⚡⚡ Fastest Blog, landing pages
SSR
Server-Side Rendering 		Each request ⚡⚡ Fast User dashboards, personalized content
ISR
Incremental Static Regeneration 		Build + background updates ⚡⚡⚡ Fastest + Fresh E-commerce products, news sites
CSR
Client-Side Rendering 		In browser ⚡ Slowest initial load Interactive apps, private data

💡 You can mix strategies in the same app - choose the best for each page!

Which Strategy Should I Use?

Decision guide for data fetching

✅ Use SSG when:

  • Content doesn't change often
  • Same for all users
  • Can be pre-rendered
  • Examples: Blog posts, about pages
// Default in Next.js - just fetch!
export default async function Blog() {
  const posts = await getPosts();
  return <PostList posts={posts} />
}

✅ Use SSR when:

  • Data changes frequently
  • Personalized per user
  • Need request data (cookies)
  • Examples: Dashboards, shopping carts
// Use cookies(), headers(), or searchParams
export default async function Dashboard() {
  const session = cookies().get('session');
  const data = await getUserData(session);
  return <Dashboard data={data} />
}

Which Strategy Should I Use? (continued)

Decision guide for data fetching

✅ Use ISR when:

  • Want static speed + fresh data
  • Content updates occasionally
  • Lots of pages (1000s)
  • Examples: Product pages, news articles 
// Revalidate every 60 seconds
export const revalidate = 60;

export default async function Product() {

✅ Use CSR when:

  • Private/sensitive data
  • Highly interactive UI
  • No SEO needed
  • Examples: Admin panels, real-time charts

export default function RealTimeChart() {
