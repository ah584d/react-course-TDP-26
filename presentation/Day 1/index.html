Reminder: What Is the DOM?

When the browser reads your HTML, it creates a tree of objects representing the page's elements. This is the DOM — Document Object Model.

The HTML you write 
<body>
  <div id="root">
    <h1>Hello, React!</h1>
    <p>Welcome to the course.</p>
  </div>
</body>
The browser's element tree 
body
└── div#root
    ├── h1
    └── p

The HTML is what you write. The DOM is the browser's representation of it, which JavaScript can read and change.

This is an HTML body excerpt; a complete document also has the html and head elements. Each nested element corresponds to a branch in the browser's DOM tree. The simplified diagram shows elements and omits their text nodes; the h1 and p also contain text. The root label is just the div's id, not a special HTML element. Establish this browser concept before showing how JavaScript selects a node. Do not introduce React's virtual DOM on this slide.

Changing the Page with JavaScript

To change what the user sees, JavaScript can find an element in that tree and change its content.

const heading = document.querySelector('#root h1');
heading.textContent = 'Hello, Dan!';
Hello, React! → Hello, Dan!
  • querySelector finds the heading.
  • textContent replaces its text.
  • The browser displays the change; the original HTML file is unchanged.

JavaScript can also create elements, add them to the tree, or remove them.

You write the steps that change the page's elements.

Use the HTML from the DOM reminder and run this script after those elements exist. Trace the selector from div#root to its h1 and show the visible text changing. textContent changes the browser's live DOM, not the source file on disk. This example assumes the selector matches; in production code handle missing elements appropriately. Mention createElement, append, and remove as other ways to change the tree without introducing more code. Next contrast these manual steps with React, still without JSX syntax.

Changing a Heading: JavaScript vs. React

In an HTML + JavaScript website

To change what the user sees, you use JavaScript to find or create an element, then rewrite its content.

In React

You write code that says what the page should show based on your data. When you update that data through React, React changes the elements on the page for you—you don't need to find, create, or rewrite them yourself.

Both approaches can update individual elements. React saves you from writing the element-update steps yourself.

React handles changing the page.
We will learn how to write the page and update its data shortly.

Build directly on the DOM reminder and JavaScript example rather than repeating their code. Learners have just seen manual element updates; now explain what React takes over. React does not replace JavaScript: we still write JavaScript, but React handles the browser element updates. The React heading will be written in JSX later, and updating the name will use props or a state setter; assigning an ordinary variable alone does not notify React. Do not introduce those APIs here. This concrete contrast explains the Declarative card from What is React? without requiring the term. The next slides explain how React updates browser elements.

How React Updates the Page

Calculate the UI → Compare with the previous result → Apply necessary DOM changes
Virtual DOM

A common name for React's in-memory representation of the UI. Not another visible page.

Real DOM

The browser's elements, text, and attributes.

Comparing the next UI description with the previous one is called reconciliation. React works out which browser elements need updating.

React figures out and applies the element updates. With plain JavaScript, you write those update steps yourself.

Unpack Smart Updates from What is React? without assuming familiarity with JSX or component functions. Explain DOM as the browser's representation of the page. Virtual DOM is useful informal vocabulary for React's in-memory UI representation, not an exact duplicate of the browser DOM or a hidden page. Reconciliation determines how the new result relates to the previous UI; commit applies changes to the real DOM. On initial display there is no previous mounted UI, so React creates the initial DOM. Avoid Fiber internals, tree-diff algorithms, and claims that the virtual DOM is automatically faster than direct DOM code. JSX syntax comes after setup.

Does React Replace Everything?

Previous result

Hello, React!

Next result

Hello, Dan!

  1. Render: calculate the next UI.
  2. Commit: apply necessary changes to the real DOM.
  3. Browser paint: display the updated page.

No. Here, React can keep the same heading element and change its text—just as our plain JavaScript example did. If the result is unchanged, no DOM change may be needed.

Calculating the UI again does not necessarily mean replacing—or even changing—the DOM.

This answers a question about React's behavior, not a claim that plain JavaScript rebuilds the page. querySelector finds an existing element; assigning textContent retains that element while replacing its text content. Both approaches can make targeted updates. React's distinction is managing those update steps for us. These are two alternative results at the same position, not two headings displayed together. Because the heading type and position remain the same, React can retain the h1 element and update its text during commit. Rendering calculates what is wanted; it is distinct from mutating DOM nodes. The browser then paints the page. A new render can produce the same result and require no DOM changes. Later, state setters will provide a reason to calculate the UI again. Reference for the teacher: https://react.dev/learn/render-and-commit. Avoid promising that React always retains every node: changes in element type or identity can replace nodes.

JSX Rules

Single root element

Wrap siblings in a <div> or Fragment

// ❌ Two roots
return (
    <h1>Hi</h1>
    <p>Bye</p>
);

// ✅ Fragment wrapper
return (
    <>
        <h1>Hi</h1>
        <p>Bye</p>
    </>
);
{} for expressions

Embed any JS expression

<h1>{user.name}</h1>          // ✅
<p>{2 + 2}</p>                 // ✅
<img src={avatarUrl} />       // ✅
Walk through each rule. 1) Single root — JSX compiles to a function call, and a function can only return one value; Fragment avoids extra DOM nodes. 2) Curly braces are the "escape hatch" into JavaScript — any expression works (variables, math, function calls, ternaries) but NOT statements (if/for). function Greeting() {

  1. React calls Greeting.
  2. The function returns a description of the heading.
  3. If React needs to render it again, it runs the function again to get the next result.

Receiving Props

React collects the named inputs into one object, which we call props.

Parent — App.tsx 
import Greeting from './Greeting';

export default function App() {
  return <Greeting name="Dan" />;
}
Child — Greeting.tsx 
type GreetingProps = { name: string };

export default function Greeting(props: GreetingProps) {
  return <h1>Hello, {props.name}!</h1>;
}

The type GreetingProps enforces the shape — TypeScript will error if name is missing or the wrong type.

Trace name="Dan" from the parent into a single props object with a name field. The child reads props.name. GreetingProps describes the required fields and their types; demonstrate a missing name or a number causing a TypeScript error. Keep object access explicit here. The next slide introduces destructuring as equivalent JavaScript shorthand, not a different React mechanism.

Destructuring Props

Same props object, shorter access. This is JavaScript shorthand, not a new React feature.

type GreetingProps = { name: string };

function Greeting(props: GreetingProps) {
  return <h1>Hello, {props.name}!</h1>;
}

Extract name directly in the parameter:

function Greeting({ name }: GreetingProps) {
  return <h1>Hello, {name}!</h1>;
}

The parent still writes <Greeting name="Dan" />. Only the child's syntax changes.

Compare the two alternative definitions; they are not two functions to copy into one file. Destructuring pulls name out of the same props object received on the preceding slide. GreetingProps and the parent's usage do not change. It is equivalent to reading props.name, and students will see this shorter form in examples.

Events in React

HTML 
<button
  onclick="handleClick()"
>
  Click me
</button>
React 

// MyButton.tsx
function MyButton() {
  const handleClick = () => {
    alert('Clicked!');
  };
  return (
    <button onClick={handleClick}>
      Click me
    </button>
  );
}
export default MyButton;
Key differences from HTML: 1) camelCase (onClick not onclick), 2) Pass a function reference, don't call it, 3) No quotes around the handler. React uses synthetic events that wrap native browser events for cross-browser consistency. The event object is passed automatically as the first argument.

Event Handler Rules

camelCase

Use camelCase prop names


<button onclick={fn}>    // ❌
<button onClick={fn}>     // ✅
Pass a function

Don't call it — pass the reference


<button onClick={handleClick()}>  // ❌
<button onClick={handleClick}>    // ✅
Common mistake: writing onClick={handleClick()} — this CALLS the function immediately on render instead of waiting for a click. The inline arrow form is useful when you need to pass arguments. Walk through each rule with the class.

Events with Parameters

Wrap in an arrow function 
function ProductList() {
  function handleDelete(id: number) {
    console.log('Delete product', id);
  }
  return (
    <button onClick={() => handleDelete(1)}>Delete</button>
  );
}
❌ Won't work 
onClick={handleDelete(1)}

Calls it immediately on render

✅ Works 
onClick={() => handleDelete(1)}

Passes a new function that calls it on click

Build on the handler rule students have just learned: we still pass a function instead of calling during render. The new idea is supplying an argument. The arrow function waits for the click and then calls handleDelete(1). Its being recreated on each render is fine here; keep performance details for later.

Why Didn't the Page Update?

The console count increased. The displayed count stayed at zero.

Changing a local variable does not tell React to run the component again.

We need a way to:
  • Store the counter's current value.
  • Update that value and tell React to calculate the UI again.
  • Keep the updated value when React runs the component again.

Rendering again means running the component function again.
With let count = 0, that line would run again too, creating a new local count starting at zero.

React calls this component-owned memory state.

Start from the demo students just saw, rather than introducing another counter or repeating its code. Clicking changes the variable captured by the handler but does not notify React, so the log increases while the page stays at zero. React does not watch ordinary variable assignments: we update state through its setter to request a render. Reveal the local-variable explanation after the three requirements: asking for another render alone would not supply memory, because let count = 0 would run again. This is conditional, not something the broken demo did after each click. No manual render control is needed. State supplies component-owned memory, unlike props supplied from outside. Its setter provides the way to request a render.

State with useState

useState is a built-in React Hook that lets a component remember a value between renders. Its setter requests an update, so React runs the component again to calculate what to show.

const [count, setCount] = useState<number>(0)

const [value, setValue] = useState<T>(initialValue)

With useState, React remembers the updated count and gives it back to the component on the next render. The initial 0 does not reset it.

count

State value for this render

setCount

Queues an update and requests a new render

0

Initial value

number

State type (T)

Connect this to the two problems with let: React remembers state between renders, and the setter requests a render when the state changes. The useState hook returns a tuple: [currentValue, setterFunction]. T is a placeholder for the state type, such as number: useState<number>(0). This makes count a number and setCount accept a number or an updater that returns a number. For simple initial values, TypeScript infers the type, so useState(0) is also typed as number. The initial value is only used on the very first render.

Rules of Hooks

  • Call useState at the component's top level, before early returns, not inside conditions, loops, or handlers.
  • Call the setter, setCount, inside the click handler.
function Counter() {
  const [count, setCount] = useState<number>(0);
  function increaseCount() {
    setCount(count + 1);
  }
  return <button onClick={increaseCount}>Count is {count}</button>;
}

Declare the hook in the component; call its setter in the handler.

Establish placement before the live fix: useState is at the component's top level; its setter is not a hook and can be called in the click handler. Hooks may only be called in React function components or custom hooks, and React needs hook calls in the same order on every render. The setter can also be used in other appropriate callbacks, not only click handlers. This direct setter performs one increment. Keep functional updaters for after snapshots and custom hook implementation for later in the course.

Connect the working demo to render and commit: React calls Counter() again, and useState returns [1, setCount]. The initial zero is not reapplied: React remembers the updated state for this mounted component. React calculates the next UI, commits the changed count text while retaining the button element, and the browser displays the update. This cycle repeats every click. The function runs again from top to bottom; a re-render does not mean rebuilding all its DOM.

State Is a Snapshot

// In this render, count is 0
function increaseCount() {
  setCount(count + 1); // Queues an update to 1
  console.log(count); // Logs 0, not 1
}
  • Queue the update: setCount(1) requests the next state.
  • Finish the handler: the log prints this render's count, which is still 0.
  • Render again: React supplies count = 1 and updates the displayed number.

The setter queues an update. React finishes the handler, then renders with the updated state. The current handler still reads the current render's value.

Starting at zero, click once: the log is zero but the new UI shows one. A new render is a separate call to the component with its own state snapshot; it does not change values captured by the already-running handler. A functional updater would also leave this console.log(count) printing zero. Awaiting the setter does not change the current render's variable. The next slide explains how React groups updates before rendering. Keep flushSync and scheduling edge cases out of this introduction.

Batching State Updates

React groups updates from the same event handler, instead of rendering after every setter call.

const [count, setCount] = useState<number>(0);
const [message, setMessage] = useState<string>('Ready');

function increaseCount() {
  setCount(count + 1);
  setMessage('Clicked');
}
  1. Queue both updates.
  2. Finish the synchronous handler code.
  3. Render with both updated values: 1 and 'Clicked'.

Why batch? Avoid unnecessary renders and a half-updated UI. Each separate click is handled separately.

What if we update the same state value twice in one handler?

Introduce batching separately from snapshots: snapshots explain which values the handler reads; batching explains why multiple setter calls are grouped before the UI updates. These two state declarations belong at the top level of the Counter component; increaseCount is its click handler. Imagine displaying message beside the count. Starting at zero and Ready, one click requests count one and message Clicked. React finishes the synchronous event-handler code, then processes the queued updates together, so the UI displays both updated values without an intermediate commit showing only one change. Do not promise an exact number of component function calls: development checks and React scheduling can run render code more than once. This does not mean waiting for future timers, network requests, or all code after an await. Modern React also supports automatic batching outside event handlers, but those scheduling details are not needed here. Separate intentional clicks are handled separately. No manual render call is necessary. The next slide applies batching and snapshots to two updates of the same count, motivating functional updaters. Reference: https://react.dev/learn/queueing-a-series-of-state-updates

Functional Updates

One setCount(count + 1) worked in our counter. Starting at 0, what if we call it twice in one handler?

Two updates in one handler 
function increaseCountByTwo() {
  setCount(count + 1);
  setCount(count + 1);
}
❌ Lost increment: final count is 1

Both count + 1 expressions still calculate 0 + 1, so React gets “set to 1” twice, not “add 1” twice.

✅ Both increments apply 
function increaseCountByTwo() {
  setCount(previousCount =>
    previousCount + 1);
  setCount(previousCount =>
    previousCount + 1);
}
// Final count: 2

Functional updaters calculate from each previous pending result, so the second adds to 1 and produces 2.

The setter queues an update; it does not change count directly inside this handler.

Initially, only the question and direct-update example are visible. Ask students to predict the final count starting from zero. On the first advance, reveal the lost increment and its explanation. On the second advance, reveal the functional-update pane and the takeaway together. The X marks the two-increment example, not every direct setter: setCount(count + 1) is valid for a single increment, and setCount(0) is appropriate for a reset. In one handler, count stays at the value from that render. Two direct increments therefore queue the same replacement value, losing one increment. Functional updaters are processed in order, each receiving the previous pending state. A similar race-condition-like lost update can happen when delayed callbacks capture the same old count; functional updates avoid that stale-state problem for increments, but do not solve every async race, such as out-of-order network responses. Updaters must stay pure. Students will use this pattern in the counter exercise; Day 2 explores queues and batching in more detail.

onChange: Reading an Input

How do we find out what the user typed?

import type { ChangeEvent } from 'react';

function NoteInput() {
  function handleChange(event: ChangeEvent<HTMLInputElement>) {
    console.log(event.target.value);
  }

  return <input type="text" onChange={handleChange} />;
}
  • As you edit, React calls handleChange with an event object describing the change.
  • event.target is the input you edited; event.target.value is its current text.
  • ChangeEvent<HTMLInputElement> tells TypeScript the event comes from an HTML input, so it knows event.target.value is a string.

As you type “Hello”, the handler logs each change:
"H", "He", "Hel", "Hell", "Hello"

Compare onChange with onClick: both receive a function, and React supplies the event. ChangeEvent types the input event so TypeScript understands target.value. Typing Hello normally logs H, He, Hel, Hell, then Hello: the handler runs for each edit, not only when typing finishes. This input works without useState because the browser manages its value. Listening to changes does not make it controlled.

Who Owns the Input's Value?

The input already displays what I type. Isn't it managing itself?

Uncontrolled input

The browser's input element holds the current value.

<input
  onChange={handleChange}
/>

React can listen to changes without supplying the value.

Controlled input

React state is the source of truth for the value.

<input
  value={note}
  onChange={handleChange}
/>

React supplies value; the handler updates that state.

Listening is not the same as controlling. Both approaches are valid.

❌ Controlled, but missing the update: <input value={note} />
For an editable controlled input, the handler must update note. Without that update, React keeps displaying the supplied value and the input is effectively read-only.

In the uncontrolled snippet, handleChange can simply log the text as on the previous slide. In the controlled snippet, it must update note, which we will wire shortly. Controlled describes where the displayed value comes from, not whether an input accepts user interaction. Uncontrolled inputs are useful too; do not frame them as incorrect. Reveal the missing-update warning after establishing that both approaches are valid: the X marks an intended editable controlled input with an incomplete update loop, not an uncontrolled input. Intentionally read-only controlled inputs can use readOnly. Keep refs and defaultValue for a later discussion.

Why Let React Control It?

Just like our counter, the component still owns its state.

NoteInput owns note. The browser's <input> displays the supplied value and reports edits through onChange.

One value can drive the rest of the UI
  • Display the note elsewhere on the page.
  • Validate it as the user types.
  • Clear it with a button.
  • Enable or disable submission based on its contents.

We are not removing component-owned state. We are making the input and the rest of the UI use the same state.

Distinguish the React component NoteInput from the HTML input element it renders. The counter used React state and passed count to a button's text; NoteInput can own React state and pass note to an input's value. Controlled does not require lifting state to a parent. An HTML input has built-in browser behavior that can manage text without React state, unlike an ordinary button that does not automatically count clicks. We choose React ownership when other UI or logic needs the same value.

Controlled Inputs: Connecting the Pieces

import { useState } from 'react';
import type { ChangeEvent } from 'react';

function NoteInput() {
  const [note, setNote] = useState<string>('');
  function handleChange(event: ChangeEvent<HTMLInputElement>) {
    setNote(event.target.value);
  }
  return (
    <div>
      <input value={note} onChange={handleChange} />
      <p>Note: {note}</p>
    </div>
  );
}
Earlier we logged the text; now setNote stores it in React state.
Input becomes “Hi” → setNote("Hi") queues an update → the next render supplies “Hi” to the input and the paragraph.
Walk through the example in stages: declare string state, read the typed event in the handler, then connect value and onChange and display the same state in a paragraph. Highlight setNote: earlier handleChange only logged the text; now it stores the text in React state. Initialize note to an empty string and keep value a string throughout the input's lifetime. The empty string gives an empty input and an empty preview. On the edit that makes the input Hi, the handler reads Hi and requests a render with that state. A direct setter is appropriate because the new text comes from the event, not a calculation from previous state. If asked about a missing handler, explain that a value without onChange or readOnly produces React's warning about a read-only field; intentionally read-only inputs can use readOnly. An onChange that only logs does not complete the controlled loop: it must update note. An uncontrolled input is still valid, because React does not supply its value. Controlled Inputs: Updating from Code

Now React can clear it too 
import { useState } from 'react';
import type { ChangeEvent } from 'react';

function NoteInput() {
  const [note, setNote] = useState<string>('');
  function handleChange(event: ChangeEvent<HTMLInputElement>) {
    setNote(event.target.value);
  }
  return (
    <div>
      <input value={note} onChange={handleChange} />
      <p>Note: {note}</p>
      <button onClick={() => setNote('')}>
        Clear note
      </button>
    </div>
  );
}
State can change through typing or through our code. Click “Clear note” → setNote('') queues an update → the next render clears the input and the preview text together.
Point out the button inside the returned div, alongside the input and the paragraph. It uses the same setNote setter as the input handler. React supplies the empty string to the input's value and to the note inside the paragraph; the paragraph's static Note: label remains. This demonstrates why React ownership is useful: the same state drives multiple places, whether edited by the user or reset by our code. Setting an empty string directly is appropriate for a reset.
