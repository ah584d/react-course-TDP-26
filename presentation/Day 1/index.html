What is React?

A JavaScript library for building user interfaces

🧩

Component-based

Like LEGO — small reusable pieces

📝

Declarative

Tell React what to show, it handles the rest

⚡

Smart Updates

Only re-renders what changed

The most widely used UI library — backed by Meta, massive ecosystem.

Key distinction: React is a LIBRARY, not a framework (unlike Angular). It handles just the View layer. Ecosystem is massive — React Router, Redux/Zustand, React Query, testing with Vitest/RTL. React dominates job listings. Compare briefly: Angular = opinionated full framework, Vue = similar but smaller community.

What is Vite?

A fast build tool for React apps. Starts instantly, updates without reload.

Replaces the old Create React App — much faster.

Vite (French for "fast") uses native ES modules in dev — no bundling needed. Only the file you changed gets sent to the browser. CRA is deprecated since 2023 — Vite is the recommended replacement. Students will see HMR in the demo.

App Component (Concept)

  • App.tsx is the root component
  • Child components nest inside parents
  • Builds UIs from small, reusable pieces
  • Every React app has exactly one root
Component Tree 
App
├── Header
├── Greeting
│   └── Avatar
└── Footer
Think of it like a family tree. App is the grandparent. Each component can have children. This tree structure is how React knows what to render and in what order. Draw parallel to HTML DOM tree — same concept, but with your custom components. Ask: "If Greeting re-renders, does Header also re-render?" Answer: by default no, only the subtree.

Your First Function Component

  • A function that returns JSX
  • Name must start with a capital letter
  • Reusable — use <Greeting /> anywhere
  • export default makes it importable

// Greeting.tsx
import React from 'react';

function Greeting() {
  return (
    <h1>Hello, React! 👋</h1>
  );
}

export default Greeting;
Stress the naming convention: PascalCase = component (Greeting), camelCase = regular function. React distinguishes components from HTML elements by the capital letter. The `import React` line is no longer needed in React 17+ with the new JSX transform, but shown here for clarity. Ask: "What happens if we name it `greeting` lowercase?" — React treats it as an HTML tag.

JSX

Looks like HTML, but it's JavaScript — gets compiled to function calls at build time.

✍️ You write


// Greeting.tsx
function Greeting() {
  const name = 'React';
  return <h1>Hello, {name}!</h1>;
}

⚙️ Under the hood — React 19 JSX transform


import { jsx as _jsx } from 'react/jsx-runtime';
const name = 'React';
_jsx("h1", { children: ["Hello, ", name, "!"] });
JSX is NOT HTML — it's syntactic sugar that compiles to function calls. This transformation is done by Babel (or SWC in Vite) at build time — it converts JSX into regular JavaScript function calls. The new JSX transform (React 17+) means you don't need `import React` at the top anymore. We'll cover the key JSX syntax rules on the next slide.

JSX Rules

Single root element

Wrap siblings in a <div> or Fragment

// ❌ Two roots
return (
    <h1>Hi</h1>
    <p>Bye</p>
);

// ✅ Fragment wrapper
return (
    <>
        <h1>Hi</h1>
        <p>Bye</p>
    </>
);
{} for expressions

Embed any JS expression

<h1>{user.name}</h1>          // ✅
<p>{2 + 2}</p>                 // ✅
<img src={avatarUrl} />       // ✅
Walk through each rule. 1) Single root — JSX compiles to a function call, and a function can only return one value; Fragment avoids extra DOM nodes. 2) Curly braces are the "escape hatch" into JavaScript — any expression works (variables, math, function calls, ternaries) but NOT statements (if/for). Mention className/htmlFor briefly if it comes up naturally during exercises.

Props

📦 Data Down

Props flow one-way — from parent to child only.

🔒 Read-Only

A child never mutates its own props.

Props are how parents talk to children. One-way data flow is a core React principle — makes debugging easy because data always flows downhill. If a child needs to communicate back, it calls a callback function passed as a prop (we'll see this later with lifting state up).

Props Example

Parent — App.tsx 
import Greeting from './Greeting';

export default function App() {
  return <Greeting name="Dan" />;
}
Child — Greeting.tsx 
type GreetingProps = { name: string };

export default function Greeting({ name }: GreetingProps) {
  return <h1>Hello, {name}!</h1>;
}

The type GreetingProps enforces the shape — TypeScript will error if name is missing or the wrong type.

Walk through both sides: child declares what it expects via a type, parent passes the actual value. Show what happens if you omit `name` or pass a number — TS red squiggles. Destructuring in the function signature is the idiomatic React pattern. Mention: you can also use `interface` instead of `type`.

How Props Work

Flexible names, many values

Names belong to the component API; a component can receive as many props as needed.

<ProductCard
  title="Mug"
  price={12}
  inStock={true}
/>
One props object

React passes the values together in one object, often named props.

function Greeting(props: GreetingProps) {
  return <h1>{props.name}</h1>;
}
Destructuring is shorthand

JavaScript can pull a value directly from the props object.

function Greeting({ name }: GreetingProps) {
  return <h1>{name}</h1>;
}
Props are read-only inputs

The parent supplies values; the child receives them for rendering.

<Greeting name={userName} />
Describe props as named values passed from parent to child. A component can receive multiple props; React collects them in one object argument. `props` is the parameter name we choose by convention, and destructuring is JavaScript shorthand for accessing its fields. Props are inputs, not values the child mutates.

Events in React

HTML 
<button onclick="handleClick()">
  Click me
</button>
React 

// MyButton.tsx
function MyButton() {
  const handleClick = () => {
    alert('Clicked!');
  };

  return (
    <button onClick={handleClick}>Click me</button>
  );
}

export default MyButton;
Key differences from HTML: 1) camelCase (onClick not onclick), 2) Pass a function reference, don't call it, 3) No quotes around the handler. React uses synthetic events that wrap native browser events for cross-browser consistency. The event object is passed automatically as the first argument.

Events with Parameters

Wrap in an arrow function 

// ProductList.tsx
function ProductList() {
  function handleDelete(id: number) {
    console.log('Delete product', id);
  }

  return (
    <ul>
      <li>
        Headphones
        <button onClick={() => handleDelete(1)}>
          Delete
        </button>
      </li>
    </ul>
  );
}
❌ Won't work 
onClick={handleDelete(1)}

Calls it immediately on render

✅ Works 
onClick={() => handleDelete(1)}

Passes a new function that calls it on click

When you need to pass an argument, wrap the call in an arrow function. The arrow function is created fresh on each render — that's fine for most cases. Stress again: onClick={handleDelete(1)} is the classic beginner bug — it fires on render, not on click. The arrow function defers the call until the user actually clicks.

Event Handler Rules

camelCase

Use camelCase prop names


<button onclick={fn}>    // ❌
<button onClick={fn}>     // ✅
Pass a function

Don't call it — pass the reference


<button onClick={handleClick()}>  // ❌
<button onClick={handleClick}>    // ✅
Common mistake: writing onClick={handleClick()} — this CALLS the function immediately on render instead of waiting for a click. The inline arrow form is useful when you need to pass arguments. Walk through each rule with the class.

State & useState Hook

🗃️ What is state?

Data owned by a component that can change over time.

const [value, setValue] = useState(initialValue)
value

Current state value

setValue

Setter — triggers re-render

initialValue

Used on first render only

🔄 Re-renders on change

Calling the setter tells React to re-render with the new value.

State is the BIG concept of the day. Props = data from outside, State = data owned internally. When state changes, React re-renders the component automatically. The useState hook returns a tuple: [currentValue, setterFunction]. The initial value is only used on the very first render.

useState in Action


// ProductCard.tsx
import { useState } from 'react';

function ProductCard() {
  const [count, setCount] = useState(0);

  function handleAddToCart() {
    setCount(count + 1);
  }

  return (
    <button onClick={handleAddToCart}>
      Add to Cart ({count})
    </button>
  );
}

export default ProductCard;

🏁 Initial Render

useState(0) returns [0, setCount].

UI: "Add to Cart (0)"

Walk through the ProductCard step by step. useState(0) sets initial count to 0. The button's onClick calls handleAddToCart which fires setCount with count + 1. Show this live in the demo project — students should follow along.

useState in Action


// ProductCard.tsx
import { useState } from 'react';

function ProductCard() {
  const [count, setCount] = useState(0);

  function handleAddToCart() {
    setCount(count + 1);
  }

  return (
    <button onClick={handleAddToCart}>
      Add to Cart ({count})
    </button>
  );
}

export default ProductCard;

🖱️ Button Clicked

handleAddToCart() → setCount(count + 1) fires.

React queues 0 → 1 & re-renders.

When the button is clicked, setCount is called with count + 1. React doesn't update immediately — it queues the update and schedules a re-render. Note: this direct form works fine for simple cases. We'll see the functional updater form next, which is safer when updates depend on previous state.

useState in Action


// ProductCard.tsx
import { useState } from 'react';

function ProductCard() {
  const [count, setCount] = useState(0);

  function handleAddToCart() {
    setCount(count + 1);
  }

  return (
    <button onClick={handleAddToCart}>
      Add to Cart ({count})
    </button>
  );
}

export default ProductCard;

🔄 Re-render

count is now 1.

UI: "Add to Cart (1)" ✓

On re-render, React calls ProductCard() again. This time useState returns [1, setCount]. The button text updates. This cycle repeats every click. Key insight: the component function runs again from top to bottom on every re-render.

State Is a Snapshot

function handleAddToCart() {
  setCount(count + 1);
  console.log(count); // the value from this render
}
  • The handler reads the state from the render that created it.
  • The setter requests a new render; it does not assign to count.
  • The next render receives the updated state.
Starting at zero, click once: the log is zero but the new UI shows one. This is not a failed update, and awaiting the setter does not change the current render's variable. Keep the explanation practical; Day 2 covers multiple queued updates and batching in detail.

Functional Updates


// Set a value calculated from this render
setCount(count + 1);

// Calculate from the previous pending state
setCount(previousCount => previousCount + 1);

Use the functional form whenever the next value depends on the previous one.

The direct form is valid for a single increment. Introduce the functional form as a clear expression of an update that depends on previous state. React passes previous pending state to the updater; the updater returns the next value and must stay pure. Students will use it in the counter exercise. Leave multiple-update queues and batching demonstrations to Day 2.

Rules of Hooks

  • Call hooks at the top level, before early returns: not in conditions, loops, or event handlers.
  • Call hooks only in React function components or custom hooks.
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(previousCount => previousCount + 1)}>
    {count}
  </button>;
}

Declare the hook in the component; call its setter in the handler.

Keep this to the two practical rules. React needs hook calls in the same order on every render. Point out that the setter is not a hook, so it belongs in the click handler. Custom hooks are another allowed location, but their implementation comes later in the course. Do not introduce effects or a custom useToggle implementation here.

onChange: Reading an Input

import type { ChangeEvent } from 'react';

function NoteInput() {
  function handleChange(event: ChangeEvent<HTMLInputElement>) {
    console.log(event.target.value);
  }

  return <input type="text" onChange={handleChange} />;
}

React calls the handler as you type. Read the new text from event.target.value.

Compare onChange with onClick: both receive a function, and React supplies the event. ChangeEvent types the input event so TypeScript understands target.value. This example logs text but does not store it; the next slide connects the input to state.

Controlled Inputs

import { useState } from 'react';
import type { ChangeEvent } from 'react';

function NoteInput() {
  const [note, setNote] = useState('');
  function handleChange(event: ChangeEvent<HTMLInputElement>) {
    setNote(event.target.value);
  }
  return <div>
    <input value={note} onChange={handleChange} />
    <p>Note: {note}</p>
  </div>;
}

value comes from state; onChange updates that state.

Trace typing to handler to setter to next render. Initialize note to an empty string and keep value a string. Supplying value without an updating onChange makes an input read-only. Setting text directly is appropriate because it comes from the event, not previous state. The podcast exercise combines this with an independent numeric likeCount state variable.
