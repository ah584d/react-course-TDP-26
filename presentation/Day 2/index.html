Why Keys Matter ?

  • Keys help React identify which items changed.
  • Without keys, React might re-render the entire list unnecessarily.
  • Keys must be unique and stable across renders.
  • Example: Using index as a key is okay for static lists but not for dynamic lists where items may move or be deleted.

💡 Let's see what happens without proper keys

Understanding Keys: Index vs Unique ID

What happens when you use array index as key?

When you use the array index as a key, React identifies each element by its position in the array, not by what it actually contains.

Array with indexes:
[0] → Buy Eggs
[1] → Buy Milk
[2] → Buy Bread

The Problem with Index Keys

🐛 What goes wrong when list items are deleted?

If you delete an item from the middle of the list, all items after it shift up and get new indexes.

Before deleting "Buy Milk":
[0] → Buy Eggs
[1] → Buy Milk 🗑️
[2] → Buy Bread
After deleting:
[0] → Buy Eggs
[1] → Buy Bread ← Changed from [2] to [1]!
React thinks: "The item at index [1] changed from 'Buy Milk' to 'Buy Bread', so I'll re-render it but keep its old state (like input values)!"

The Solution: Use Unique IDs

✅ Unique IDs stay with each item

Use unique IDs that stay with each item regardless of its position. When an item is deleted, React knows exactly which one is gone.

Before deleting "Buy Milk":
key={101} → Buy Eggs
key={102} → Buy Milk 🗑️
key={103} → Buy Bread
After deleting:
key={101} → Buy Eggs
key={103} → Buy Bread ← Still key={103}, just moved up!

React knows: "key={102} was removed, key={103} is still the same item, just preserve its state!"

Key source Rating When

Conditional Rendering

  • Conditional rendering is the ability to show or hide components or elements based on certain conditions (state, props, or data).
  • It is similar to if/else statements in programming but adapted for JSX.

Why Conditional Rendering Matters

  • Better UX: Shows context-sensitive content that's relevant to the user's current state
  • Performance: Avoids unnecessary DOM elements and reduces render load
  • Dynamic UI: Makes your interface responsive to user state and interactions

Ternary Operator (? :)

When to use it

Use the ternary operator when you need to choose between two options.

Syntax: condition ? renderThisIfTrue : renderThisIfFalse

Ternary Operator - Example

function LoginButton({ isLoggedIn }) {
  return (
    <button>
      {isLoggedIn ? 'Logout' : 'Login'}
    </button>
  );
}

// If isLoggedIn is true → shows "Logout"
// If isLoggedIn is false → shows "Login"

Logical AND (&&)

When to use it

Use the logical AND operator when you want to render something only if a condition is true.

Syntax: condition && renderThisIfTrue

Logical AND - Example

function Notification({ hasMessages }) {
  return (
    <div>
      {hasMessages && (
        <span className="badge">
          You have new messages!
        </span>
      )}
    </div>
  );
}

// If hasMessages is true → shows the badge
// If hasMessages is false → shows nothing

Ternary vs Logical AND

When to use which?

✅ Use ? :
  • When you have TWO alternatives
  • Show A or show B
  • Need an "else" case
✅ Use &&
  • When you have ONE option
  • Show something or nothing
  • No "else" needed
A classical situation to use && is when we want to display a modal — show the modal component or nothing (the backdrop or null).

Ternary vs Logical AND - Examples

// ✅ Good: Two options → use ternary
{isLoggedIn ? <Dashboard /> : <LoginForm />}

// ✅ Good: One option → use &&
{isPremium && <PremiumFeatures />}

// 🟠 Not best practice: avoid ternary when you only want one option
{isPremium ? <PremiumFeatures /> : null}

What is the Virtual DOM?

  • React maintains a Virtual DOM, a lightweight copy of the real DOM stored in memory.
  • Think of it as a blueprint of the UI React can compare quickly without touching the actual browser DOM.
💡 Visual Concept
🌳
Real DOM
(Heavy)
↔️
📄
Virtual DOM
(Lightweight)

How React Updates the UI Efficiently

When a component state or prop changes:

  1. React creates a new Virtual DOM tree
  2. Compares it to the previous Virtual DOM (this is called diffing)
  3. Only updates the actual DOM elements that changed, instead of re-rendering everything

Analogy: Instead of repainting an entire wall, React only touches the bricks that are cracked.

🔄 The Process
State Change → New Virtual DOM → Diff → Minimal DOM Update
Importance of Keys in Reconciliation:
  • Keys allow React to match elements between renders, making diffing fast and accurate.
  • Without keys, React may re-render the whole list even if only one item changed.

Why Hooks Exist ?

The Problem Before Hooks

Before React 16.8, state and lifecycle features were only available in class components.

Functional components were "stateless" - they could only receive props and return JSX.

The Solution: Hooks

Hooks let us use state, effects, and other React features in functional components, making them simpler and more powerful.

State & useState Hook

🗃️ What is state?

Data owned by a component that can change over time.

const [value, setValue] = useState(initialValue)
value

Current state value

setValue

Setter — triggers re-render

initialValue

Used on first render only

🔄 Re-renders on change

Calling the setter tells React to re-render with the new value.

State is the BIG concept of the day. Props = data from outside, State = data owned internally. When state changes, React re-renders the component automatically. useState returns a tuple: [currentValue, setterFunction]. The initial value is only used on the very first render.

useState in Action 


// ProductCard.tsx
import { useState } from 'react';

function ProductCard() {
  const [count, setCount] = useState(0);

  function handleAddToCart() {
    setCount(count + 1);
  }

  return (
    <button onClick={handleAddToCart}>
      Add to Cart ({count})
    </button>
  );
}

export default ProductCard;

🏁 Initial Render

useState(0) returns [0, setCount].

UI: "Add to Cart (0)"

Walk through the ProductCard step by step. useState(0) sets the initial count to 0. The button's onClick calls handleAddToCart which fires setCount with count + 1.

🖱️ Button Clicked

handleAddToCart() → setCount(count + 1) fires.

React queues 0 → 1 & re-renders.

When the button is clicked, setCount is called with count + 1. React doesn't update immediately — it queues the update and schedules a re-render.

count is now 1.

On re-render, React calls ProductCard() again. This time useState returns [1, setCount]. The button text updates. The component function runs again from top to bottom on every re-render.

State with Objects — Immutability


const [user, setUser] = useState({ name: 'Dan', age: 30 });

// ✅ spread — creates a new object
setUser(prev => ({ ...prev, age: 31 }));

// ❌ mutate — React won't re-render
user.age = 31;
Why spread?
  • React uses === to detect changes
  • Mutating the same object keeps the same reference
  • Spread creates a new object — React sees the change
  • Only the updated property changes; the rest is copied

Never mutate state directly — always return a new reference so React detects the change.

This is the #1 state bug beginners hit. React uses reference equality (===) to detect changes. Spread creates a shallow copy — that's a new reference.

State with Arrays — Immutability


const [items, setItems] = useState(['a', 'b', 'c']);

// ✅ add
setItems(prev => [...prev, 'd']);

// ✅ remove
setItems(prev => prev.filter(i => i !== 'b'));

// ❌ wrong — mutates in place!
items.push('d');
setItems(items);
✅ Immutable methods

map, filter, spread, slice, concat

❌ Mutating methods

push, pop, splice, sort (in-place), reverse

Same rule as objects — always return a new array so React sees the update.

For arrays: use map/filter/spread, never push/splice directly. Immutable methods return a new array; mutating methods modify in place.

Functional Updates & Batching


// ❌ Direct — can read stale value
setCount(count + 1);
setCount(count + 1); // still uses stale count

// ✅ Functional — always reads latest
setCount(prev => prev + 1);
setCount(prev => prev + 1); // reads the queued value

React batches multiple updates in the same event handler. State does not change immediately — it changes on the next render. Use the functional form whenever the next value depends on the previous one.

If you call setCount(count + 1) twice in the same handler, you get count+1 both times (not count+2) because count is a stale closure. The functional form receives the actual queued value. This is also why "state doesn't change immediately" — React batches and applies updates before the next render.

Rules of Hooks

  • 🔝 Call Hooks at the top level — not inside loops or conditions
  • ⚛️ Call Hooks only in React functions — components or custom hooks
  • 🔢 Order must stay the same on every render
❌ Wrong 
if (loggedIn)
  const [s, setS] = useState();
✅ Right 
const [s, setS] = useState();
if (loggedIn) { ... }
Why order matters: React tracks hook state by call order (1st useState → slot 0, 2nd → slot 1…). If a hook is inside an if, it may be skipped on some renders, shifting all subsequent slots and corrupting state.

Common mistakes to highlight:
  • Calling useState inside an if statement
  • Using hooks inside regular (non-component) functions
  • Calling a hook inside a .map() callback

useEffect for Side Effects

useEffect(
① effect
() => {
  // side effect
③ cleanup
return () => { /* cleanup */ }

}
, 
② deps
[dep1, dep2]
)
① Runs after render ② [] = once  |  [val] = on change  |  omit = every render ③ Runs on unmount / before next effect
What is a side effect? Any operation that interacts outside the component or affects something outside its scope. Examples: fetching data, timers, subscriptions, manual DOM manipulation.

When does useEffect run?
  • After every render (no dep array)
  • Only when listed dependencies change ([dep1, dep2])
  • Once after first render only ([]) — equivalent to componentDidMount
Cleanup function: Return a function from useEffect to clean up resources like intervals, subscriptions, or event listeners — prevents memory leaks.

Demo idea: effect sets setInterval → cleanup calls clearInterval.

useEffect — Key Points

  • ⏱️ Runs after the component renders — never during
  • 🔁 [] → once  |  [val] → when val changes  |  no array → every render
  • 🧹 Return a function to clean up (clear timers, unsubscribe…)
  • 🚫 No cleanup = memory leak if the component unmounts
Walk through each point with the clock example in mind:
  • setInterval starts the clock → dep array [] means it runs once
  • Cleanup calls clearInterval when the component is removed from the tree
  • Without cleanup the interval keeps ticking even after unmount — classic memory leak

Example: Clock with useEffect - Code

JavaScript/JSX 
import { useState, useEffect } from "react";

export default function Clock() {
  const [time, setTime] = useState(new Date());

  useEffect(() => {
    const timer = setInterval(() => {
      setTime(new Date());
    }, 1000);

    return () => clearInterval(timer);
  }, []);

  return (
    <h1>{time.toLocaleTimeString()}</h1>
  );
}

What is a Custom Hook?

  • A JavaScript function that starts with use and reuses component logic.
  • Can use other hooks inside it (useState, useEffect, etc.).

Why Use Custom Hooks?

  • Avoid repeating code.
  • Separate logic from UI.
  • Makes code cleaner and easier to test.

What Can Custom Hooks Return?

  • Can return any kind of data: objects, arrays, primitives, functions
  • Can return nothing (just perform side effects)
  • ❌ Cannot return JSX - hooks are logic, not UI

Custom Hooks as Services

  • Think of custom hooks as services
  • They provide reusable functionality to components
  • Similar to services in other frameworks (Angular, etc.)

Custom Hooks & Component Lifecycle

  • Custom hooks are part of the component's lifecycle
  • They execute when the component renders
  • This is just a technical/visual separation of concerns

Custom Hooks & Design Patterns

  • Similar to MVC pattern: separate business logic from presentation
  • Custom Hook = Model/Controller (logic)
  • Component = View (UI/JSX)

Custom Hooks - Example

useFetch encapsulates data fetching logic, so any component can just call const { data, loading } = useFetch(url).

💡 Show example: component without custom hook (repeated fetch code) vs component with custom hook

Example: useFetch Custom Hook

import { useState, useEffect } from "react";

export function useFetch(url) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch(url)
      .then((res) => res.json())
      .then((json) => setData(json))
      .finally(() => setLoading(false));
  }, [url]);

  return { data, loading };
}

What is useRef?

  • A hook that holds a mutable object whose .current property persists across renders.
  • Can store DOM elements or mutable values.

useRef - Use Cases

  • DOM access: Focus input, scroll to element, measure element size.
  • Mutable storage: Store previous state or timer ID without triggering re-renders.

useRef - Important Rules

  • Updating .current does not trigger a render.
  • Useful for performance-sensitive operations.

💡 Show visual: component renders, useRef stores a DOM element → manipulate it without re-rendering

Example: Focus Input with useRef

JavaScript/JSX 
import { useRef } from "react";

function FocusInput() {
  const inputRef = useRef();

  const handleFocus = () => {
    inputRef.current.focus();
  };

  return (
    <div className="focus-container">
      <input
        ref={inputRef}
        type="text"
        placeholder="Type here..."
      />
      <button onClick={handleFocus}>
        Focus Input
      </button>
    </div>
  );
}

Example: useRef - Constant Reference

JavaScript/JSX 
import { useState, useRef } from "react";

function ClickCounter() {
  const [stateCount, setStateCount] = useState(0);
  const [displayRef, setDisplayRef] = useState(0);
  const refCount = useRef(0);

  const handleStateClick = () => {
    setStateCount(stateCount + 1); // ✅ Triggers re-render
  };

  const handleRefClick = () => {
    refCount.current++; // ❌ No re-render
    console.log("Ref count:", refCount.current);
  };

  const showRefValue = () => {
    setDisplayRef(refCount.current); // Force update
  };

  return (
    <div>
      <p>State Count: {stateCount}</p>
      <p>Ref Count (Display): {displayRef}</p>
      <button onClick={handleStateClick}>
        State +1 (Re-renders)
      </button>
      <button onClick={handleRefClick}>
        Ref +1 (No Re-render)
      </button>
      <button onClick={showRefValue}>
        Show Ref Value
      </button>
    </div>
  );
}
Key Points
  • useState triggers re-render when updated
  • useRef persists value but doesn't trigger re-render
  • Perfect for tracking values like click counts, timers, previous values
  • Check console to see ref value updates
