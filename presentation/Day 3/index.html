What is a Custom Hook?

  • A JavaScript function that starts with use and reuses component logic.
  • Can use other hooks inside it (useState, useEffect, etc.).

Why Use Custom Hooks?

  • Avoid repeating code.
  • Separate logic from UI.
  • Makes code cleaner and easier to test.

What Can Custom Hooks Return?

  • Can return any kind of data: objects, arrays, primitives, functions
  • Can return nothing (just perform side effects)
  • ❌ Cannot return JSX - hooks are logic, not UI

Custom Hooks as Services

  • Think of custom hooks as services
  • They provide reusable functionality to components
  • Similar to services in other frameworks (Angular, etc.)

Custom Hooks & Component Lifecycle

  • Custom hooks are part of the component's lifecycle
  • They execute when the component renders
  • This is just a technical/visual separation of concerns

Custom Hooks & Design Patterns

  • Similar to MVC pattern: separate business logic from presentation
  • Custom Hook = Model/Controller (logic)
  • Component = View (UI/JSX)

Custom Hooks - Example

useFetch encapsulates data fetching logic, so any component can just call const { data, loading } = useFetch(url).

💡 Show example: component without custom hook (repeated fetch code) vs component with custom hook

Example: useFetch Custom Hook

import { useState, useEffect } from "react";

export function useFetch(url) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch(url)
      .then((res) => res.json())
      .then((json) => setData(json))
      .finally(() => setLoading(false));
  }, [url]);

  return { data, loading };
}

What is useRef?

  • A hook that holds a mutable object whose .current property persists across renders.
  • Can store DOM elements or mutable values.

useRef - Use Cases

  • DOM access: Focus input, scroll to element, measure element size.
  • Mutable storage: Store previous state or timer ID without triggering re-renders.

useRef - Important Rules

  • Updating .current does not trigger a render.
  • Useful for performance-sensitive operations.

💡 Show visual: component renders, useRef stores a DOM element → manipulate it without re-rendering

Example: Focus Input with useRef

JavaScript/JSX 
import { useRef } from "react";

function FocusInput() {
  const inputRef = useRef();

  const handleFocus = () => {
    inputRef.current.focus();
  };

  return (
    <div className="focus-container">
      <input
        ref={inputRef}
        type="text"
        placeholder="Type here..."
      />
      <button onClick={handleFocus}>
        Focus Input
      </button>
    </div>
  );
}

Example: useRef - Constant Reference

JavaScript/JSX 
import { useState, useRef } from "react";

function ClickCounter() {
  const [stateCount, setStateCount] = useState(0);
  const [displayRef, setDisplayRef] = useState(0);
  const refCount = useRef(0);

  const handleStateClick = () => {
    setStateCount(stateCount + 1); // ✅ Triggers re-render
  };

  const handleRefClick = () => {
    refCount.current++; // ❌ No re-render
    console.log("Ref count:", refCount.current);
  };

  const showRefValue = () => {
    setDisplayRef(refCount.current); // Force update
  };

  return (
    <div>
      <p>State Count: {stateCount}</p>
      <p>Ref Count (Display): {displayRef}</p>
      <button onClick={handleStateClick}>
        State +1 (Re-renders)
      </button>
      <button onClick={handleRefClick}>
        Ref +1 (No Re-render)
      </button>
      <button onClick={showRefValue}>
        Show Ref Value
      </button>
    </div>
  );
}
Key Points
  • useState triggers re-render when updated
  • useRef persists value but doesn't trigger re-render
  • Perfect for tracking values like click counts, timers, previous values
  • Check console to see ref value updates

What Is a Cache?

A cache = a saved copy of data we already fetched, kept close to the UI.

Start with the picture before any words. Point at the small legends: Header only shows the user name, Profile shows the full user profile - different UI, but both need the same user data. Left side: two components both need the same user. Each one calls the server, so we pay for two network trips and the user waits twice. Right side: the first request fills the cache. Every other component that asks for the same data reads the saved copy instantly. The dashed arrow shows the server is only contacted once. Then read the definition: a cache is a saved copy of data we already fetched, kept close to the UI.

Why Client Apps Need a Cache

  • Speed - show saved data instantly instead of a spinner
  • Fewer requests - the same data is fetched once, not per component
  • Less load - lighter on the server, the network, and mobile data
  • Better UX - go back to a page and it is already there
The catch: cached data can become stale. A cache must know when to refetch and when to throw data away.
Walk through the four benefits in one sentence each. Relate to the Yad2 or product list example: navigating away and back should not show a spinner again. Then name the hard part: cache invalidation. Cached data can be out of date, so someone must decide when to refetch and when to discard it. Writing this by hand with useEffect and useState is error-prone, which is exactly what TanStack Query solves on the next slide.

TanStack Query

The industry standard for data fetching in React

  • useQuery - read data and track loading / error state
  • Cache - results are stored and shared by queryKey
  • useMutation - create, update, and delete data

Replaces hand-written useEffect + useState fetching code.

Connect this to the useFetch custom hook from earlier: TanStack Query is the production-grade version of that idea. Explain that it manages loading, error, caching, and refetching so we do not write that logic by hand. Introduce the three pieces for this chapter: useQuery, the cache, and useMutation.

The Old Way


function Products() {
  const [products, setProducts] = useState([]);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState(null);
  useEffect(() => {
    fetch("/api/products")
      .then((res) => res.json())
      .then((data) => setProducts(data))
      .catch((err) => setError(err))
      .finally(() => setIsLoading(false));
  }, []);
  if (isLoading) return <p>Loading...</p>;
  if (error) return <p>Error: {error.message}</p>;
  return <ProductList products={products} />;
}
  • useEffect + useState: 3 states and 1 effect just to read data.
  • No cache, no retries, no refetching, no request de-duplication.
Show the code students already know from Day 2 and the useFetch hook. Count the pieces: three useState calls, one useEffect, manual loading and error handling. Point out what is still missing: if two components render this, two requests are sent; if we leave the page and come back, we fetch again and show the spinner again; and there is no protection against stale responses arriving out of order. This is the pain TanStack Query removes. Keep this slide in mind when we see useQuery in a few slides.

The New Way


function Products() {
  const { data, isPending, error } = useQuery({
    queryKey: ["products"],
    queryFn: () => fetch("/api/products").then((res) => res.json()),
  });
  if (isPending) return <p>Loading...</p>;
  if (error) return <p>Error: {error.message}</p>;
  return <ProductList products={data} />;
}
  • Same task: 1 hook instead of 3 states and 1 effect.
  • Cache, retries, refetching, and de-duplication come built in.
  • queryKey uniquely identifies the data in the cache.
  • queryFn returns a promise that resolves with the data.
  • The hook returns data, isPending, isError, and more.
Put this next to the previous slide: same component, same loading and error handling, same output. The three useState calls and the useEffect are replaced by one useQuery call. queryKey is the cache address, queryFn is how to fetch when the data is not cached. Because of the cache, a second component using the same key does not trigger a second request, and coming back to this page shows the saved data immediately. Next we set up the QueryClientProvider that makes this work, then look at useQuery in detail.

Setting Up TanStack Query


import { QueryClient, QueryClientProvider } from "@tanstack/react-query";

const queryClient = new QueryClient();

function App() {
  return (
    <QueryClientProvider client={queryClient}>
      <Products />
    </QueryClientProvider>
  );
}

QueryClient owns the cache

QueryClientProvider makes it available to every component

The Query Cache


useQuery({
  queryKey: ["product", id],
  queryFn: () => fetchProduct(id),
  staleTime: 60_000, // fresh for 1 minute
  gcTime: 5 * 60_000, // kept in cache for 5 minutes after unused
});
  • Same queryKey in two components = one request, shared result.
  • Fresh data is served from cache without refetching.
  • Stale data is shown instantly, then refetched in the background.
Explain the cache lifecycle: fresh, stale, and garbage collected. By default data is stale immediately, so TanStack Query refetches on mount, window focus, and reconnect. staleTime controls how long data counts as fresh; gcTime controls how long unused data stays in memory. useMutation


const queryClient = useQueryClient();

const addProduct = useMutation({
  mutationFn: (newProduct) =>
    fetch("/api/products", {
      method: "POST",
      body: JSON.stringify(newProduct),
    }),
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ["products"] });
  },
});

<button onClick={() => addProduct.mutate({ name: "Mug" })}>Add</button>
  • useMutation is for writes: POST, PUT, PATCH, DELETE.
  • mutate() triggers it; isPending tracks progress.
  • invalidateQueries marks cached data stale so the list refetches.
Contrast with useQuery: queries read and run automatically, mutations write and run on demand. The key pattern is invalidateQueries in onSuccess, which keeps the cached list in sync after a change. Mention optimistic updates as a next step but do not go deep. Teacher demo (useMutation + invalidateQueries): code/day_2_and_3 at /usemutation.

React Router: Introduction

🚦 What is React Router?

  • Library for handling navigation in React
  • Adds multiple screens without page reloads
  • Changes the URL while keeping state and context
  • Core for building SPAs
Define React Router as the library that maps a URL to a React component tree. Contrast this with traditional multi-page navigation where the whole document reloads. Emphasize that in a single-page app, navigation feels fast because React swaps views instead of rebuilding the entire page from the server.

Query Params

  • Query params are key-value pairs added after ? in the URL.
  • They help control page state such as filters, sorting, search text, or pagination.
  • Syntax: /products?category=shoes&sort=price.
  • We access the query param values with React Router's useSearchParams hook.

Example: Filtering cars list


import { useSearchParams } from "react-router-dom";

function ProductsPage() {
  const [searchParams] = useSearchParams();
  const category = searchParams.get("category");
  const sort = searchParams.get("sort");

  return <p>Category: {category}, Sort: {sort}</p>;
}
Introduce query params as an extra layer of information attached to a URL. Explain that they do not usually identify a different page, but rather describe how that page should be displayed. Use familiar examples such as filters, search text, sort order, and pagination. Mention that React Router provides useSearchParams for reading and updating query string values.

URL Params vs Query Params

URL Params

Part of the path, like /products/42.

Usually identifies a specific resource such as a product, user, or post.

Query Params

Come after ?, like /products?category=shoes&sort=price.

Usually changes how a page is filtered, sorted, searched, or paginated.

Contrast the two concepts clearly. Explain that slash-products-slash-42 points to one specific product, while query params usually modify how a list or page is displayed. Reinforce the rule of thumb: path for identity, query string for options.

Update one query parameter

import { useSearchParams } from 'react-router-dom';
const movies = [
  { title: 'Night Run', genre: 'action' },
  { title: 'Weekend Mix-Up', genre: 'comedy' },
];
export default function GenrePage() {
  const [searchParams, setSearchParams] = useSearchParams();
  const genre = searchParams.get('genre') ?? '';
  const shown = movies.filter(movie => !genre || movie.genre === genre);
  function changeGenre(nextGenre) {
    setSearchParams(previous => {
      const next = new URLSearchParams(previous);
      if (nextGenre) next.set('genre', nextGenre);
      else next.delete('genre');
      return next;
    });
  }
  return (
    <div>
      <select value={genre} aria-label="Genre" onChange={event => changeGenre(event.target.value)}>
        <option value="">All genres</option>
        <option value="action">Action</option>
        <option value="comedy">Comedy</option>
      </select>
      {shown.map(movie => <p key={movie.title}>{movie.title}</p>)}
    </div>
  );
}

The URL drives the selected filter. Copying the existing parameters preserves other options.

Trace the select change to the URL update, then back through genre to the selected option and visible movies. A direct URL or refresh restores the same selection and results.

If saving fails, stay put

const [saveError, setSaveError] = useState('');
async function handleSave() {
  setSaveError('');
  try {
    await saveProfile();
    navigate('/profile');
  } catch (error) {
    console.error('Profile save failed:', error);
    setSaveError('Could not save. Please try again.');
  }
}

Show saveError next to Save with role="alert". A failed save must not navigate.

This continues in the same component, with useState imported from React and navigate from the prior slide. A rejected save keeps the form visible and allows retry.

Relative and absolute destinations

From a component on the /settings route:

navigate('profile');  // /settings/profile
navigate('/profile'); // /profile

A leading slash starts at the app root. Without one, the destination is relative to the route.

The same distinction applies to Link's to prop. Keep route-relative .. and history replacement for later study.
