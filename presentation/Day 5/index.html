Performance Optimization

Memoization, Rendering, the React Compiler & What's New in React 19

Measure, then optimize React 19
Welcome to Day 5. Today we focus on performance optimization — understanding when and how to prevent unnecessary work in React.

What Is Memoization?

Same input → return cached result, skip the work.

const cache = {};

function double(n) {
  if (cache[n]) return cache[n];
  cache[n] = n * 2;
  return cache[n];
}

double(8); // computes → 16
double(8); // cached  → 16
Start with memoization in general before React. We save a previous result in a cache, and when the same input comes back, we skip the work and reuse the answer. This is the core idea behind React.memo, useMemo, and useCallback: avoid doing the same work again when nothing important changed.

Why Performance Optimization Matters

  • Large component trees and frequent re-renders
  • Expensive calculations or passing functions as props
  • Slow UI interactions
  • React is fast, but unnecessary re-renders hurt
  • Don't optimize until you have a real performance problem
Set the stage: React is already fast, but as apps grow, unnecessary renders accumulate. We optimize the bottlenecks, not everything.

How React Renders

(Quick Refresher)
  • A component re-renders when its state changes
  • When its props change
  • When its parent re-renders
  • By default: parent render triggers child renders
Quick refresher on the render cycle. Emphasize that parent re-renders cascade down to all children by default — this is the root cause of most perf issues.

What Is an Unnecessary Re-render?


function App() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>+</button>
      <HeavyComponent title="Products" />
    </>
  );
}

HeavyComponent re-renders even though it does not use count. Optimization helps.

Walk through the example: clicking the button changes count, Parent re-renders, and HeavyComponent re-renders for no reason. This is the problem we solve.

What Is React.memo?

  • Higher-order component
  • Memoizes a component

const MyComponent = React.memo(Component);

✓ Skips re-render if props did not change

React.memo is a higher-order component that wraps your component. It compares previous and next props — if they're the same, it skips re-rendering.

React.memo Example


const HeavyComponent = memo(({ title }: { title: string }) => {
  return <h2>{title}</h2>;
});

function App() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>+</button>
      <HeavyComponent title="Products" />
    </>
  );
}

HeavyComponent no longer re-renders when count changes — title is the same.

memo receives a function component and an optional custom comparison function. It returns a new component that behaves the same but skips re-rendering when props have not changed. Think of it as a wrapper — same component inside, with a "skip if same props" guard added on top.

Without vs With React.memo

WithoutWith
Parent renders → child always rendersParent renders → child renders only if props changed

Uses shallow comparison (===) — primitives by value, objects/arrays by reference.

Key concept: shallow comparison means === on each prop. Primitives are safe. Objects and arrays need stable references — this is where useMemo comes in later.

Shallow Comparison Examples

❌ Child ALWAYS re-renders

function Parent() {
 const [count, setCount] = useState(0);

 // new array created every render
 const items = ["a", "b", "c"];
 return <Box items={items} />;
}
✅ Child does NOT re-render

const items = ["a", "b", "c"];

function Parent() {
 const [count, setCount] = useState(0);

 // same reference every render
 return <Box items={items} />;
}

Arrays are compared by reference, not by content.
Every render creates a new reference → memo thinks props changed.

Side-by-side comparison. Left: inline array creates a new reference every render, defeating memo. Right: array defined outside the component keeps the same reference. This is the most common mistake with React.memo.

When React.memo Helps

  • Heavy components or long lists
  • UI components with stable props
  • Not useful when props change often or component is cheap
  • Rule: measure first, optimize second
Don't wrap everything in memo. It has a cost (storing previous props, running comparison). Only use when the component is expensive or renders frequently with the same props.

Why useCallback Exists


function Dashboard({ products }) {
  const [query, setQuery] = useState("");

  const handleDelete = (id: number) =>
    console.log("delete", id);

  return (
    <>
      <input value={query}
        onChange={e => setQuery(e.target.value)}
      />
      <ProductTable
        products={products}
        onDelete={handleDelete}
      />
    </>
  );
}
                            

const ProductTable = memo(({products,  onDelete,}: {
  products: Product[];
  onDelete: (id: number) => void;
}) => {
  return (
    <ul>
      {products.map(p => (
        <li key={p.id}>
          {p.name}
          <button onClick={() => onDelete(p.id)}>
            Remove
          </button>
        </li>
      ))}
    </ul>
  );
});

What is the problem in this code?

  • Functions are recreated on every render
  • ProductTable re-renders on every query change
Show the code first and ask students what the issue is. Then reveal: handleDelete is a new function reference every render, so ProductTable always re-renders even though memo wraps it. useCallback solves this.

useCallback Explained


const fn = useCallback(() => {
  /* logic */
}, [deps]);

Memoizes a function to keep the same reference between renders.

useCallback returns the same function reference between renders as long as deps haven't changed. It's the function equivalent of useMemo.

The Fix: useCallback


function Dashboard({ products }: { products: Product[] }) {
  const [query, setQuery] = useState("");

  // ✅ stable reference — same function every render
  const handleDelete = useCallback((id: number) => {
    console.log("delete", id);
  }, []);

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <ProductTable products={products} onDelete={handleDelete} />
    </>
  );
}

handleDelete keeps the same reference — ProductTable no longer re-renders on every keystroke.

Wrapping handleDelete in useCallback with an empty deps array means the function reference never changes. ProductTable's memo now works correctly — it only re-renders when products actually change.

What Is useMemo?

  • Memoizes a value
  • Avoids recalculating expensive logic on every render

const value = useMemo(() => compute(), [deps]);
useMemo caches the return value of a function. It only recomputes when dependencies change. Think of it as "remember this result until deps change." Gets: a function to run + a dependency array. Returns: the cached result of that function — not the function itself.

Problem: Expensive Calculation


function Stats({ n }: { n: number }) {
  let total = 0;
  for (let i = 0; i < n; i++) total += i; // slow

  return <p>Sum: {total}</p>;
}

Recalculates on every render — even when n hasn't changed.

Without useMemo, the filter runs on every render even if products and query haven't changed. For large lists this is wasteful.

Solution: With useMemo


function Stats({ n }: { n: number }) {
  const total = useMemo(() => {
    let sum = 0;
    for (let i = 0; i < n; i++) sum += i;
    return sum;
  }, [n]);

  return <p>Sum: {total}</p>;
}

Recalculates only when n changes.

Now the filter only runs when products or query actually change. If the parent re-renders for other reasons, this computation is skipped.

What useMemo Actually Does

  • Caches the result, not the function
  • Dependency array controls recomputation
Important distinction: useMemo caches the result, not the function itself. If you forget a dependency, you get stale data. ESLint exhaustive-deps rule helps catch this.

When to Use useMemo

  • Expensive calculations used in rendering
  • Dependencies are stable
  • Avoid for simple calculations — measure first
Simple math or string operations don't need useMemo. The overhead of memoization would be greater than the computation itself. Profile first.

Common Mistakes

  • Memoizing everything "just in case"
  • Missing dependencies in the deps array
  • Optimizing before measuring
Common pitfalls: wrapping everything in memo/useMemo adds complexity and cost without benefit. Missing deps leads to stale closures. Passing a fresh object/array/function each render silently defeats React.memo. Always profile before optimizing.

Real-World Example (Summary)

  • List component → React.memo
  • Expensive filtering → useMemo
  • Event handlers → useCallback

Meet React Compiler.

Humorous pivot — everything we just learned can be handled automatically by the compiler. But the mental model is still essential for debugging and writing correct code.

React Compiler

Introduced in React 19

🔧 Compile-time tool

Automatically optimizes re-renders at build time.

💤 Less boilerplate

Reduces the need for manual useMemo and useCallback.

🔍 Transparent

Works behind the scenes — no API changes needed.

Memoization applied automatically at compile time.

React Compiler is the future of performance in React. It analyzes your code at build time and inserts memoization automatically. No runtime cost, no manual work.

Before the Compiler


// Parent.tsx
function Parent({ value }: { value: number }) {
  const expensive = useMemo(() => {
    return heavyCalculation(value);
  }, [value]);

  return <Child data={expensive} />;
}

Manual useMemo adds cognitive overhead and boilerplate to every component.

This is what we've been writing all day — manual useMemo everywhere. It works but adds noise. The compiler eliminates this boilerplate.

With React Compiler


function Parent({ value }) {
  const expensive = heavyCalculation(value);
  return <Child data={expensive} />;
}
  • No useMemo needed
  • Same performance with cleaner code
  • Compiler tracks dependencies and memoizes
Same behavior, cleaner code. The compiler figures out what depends on what and memoizes automatically. You write simple code, the compiler optimizes it.

Why We Still Need the Hooks

  • Legacy codebases and libraries still rely on manual memoization
  • Understanding the "why" helps you debug when things go wrong
  • React Compiler runs only on components that follow React's rules
Manual memoization is still everywhere in legacy code and third-party libraries. Knowing why hooks work the way they do makes you a better debugger. And the compiler is not magic — it can only optimize components that obey React's rules.

React Rules the Compiler Checks

  • Only call Hooks at the top level of components and custom Hooks
  • Props and state are immutable; never mutate them directly
  • No side effects during render — use useEffect for side effects
The compiler can only optimize code that follows React's rules. If a component breaks purity, mutates state, or calls hooks conditionally, the compiler skips it or produces a warning. Following these rules is not just good practice — it unlocks automatic memoization.

React 19 ships more than the compiler. Over the next few slides we'll look at three everyday improvements: the use hook, simplified context, and native document metadata.

The New use Hook

Resolve promises directly in render — no more useEffect + useState for simple fetches. Pairs with <Suspense>.

Before (Older React)

function Profile({ id }) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetchUser(id).then((u) => {
      setData(u);
      setLoading(false);
    });
  }, [id]);

  if (loading) return <Spinner />;
  return <h1>{data.name}</h1>;
}

After (React 19)

function Profile({ userPromise }) {
  const data = use(userPromise);
  return <h1>{data.name}</h1>;
}

// Parent
<Suspense fallback={<Spinner />}>
  <Profile userPromise={fetchUser(id)} />
</Suspense>

<Suspense> lets a component "wait" for async work — it shows a fallback (e.g. a spinner) until the data is ready, then renders the real content.

The use hook lets you read a promise during render. Suspense handles the loading state, so you delete the useEffect/useState boilerplate entirely.

Simplified Context

Goodbye .Provider — render the context object directly as the component.

Before (Older React)

<ThemeContext.Provider value={theme}>
  <App />
</ThemeContext.Provider>

After (React 19)

<ThemeContext value={theme}>
  <App />
</ThemeContext>
You can now use the context object itself as the provider. Less nesting, less ceremony — the .Provider suffix is no longer required.

Native Document Metadata

React hoists <title>, <meta> and <link> to <head> — no document.title, no react-helmet.

Before (Older React)

function Home() {
  useEffect(() => {
    document.title = "Home";
  }, []);

  return <h1>Home</h1>;
}

After (React 19)

function Home() {
  return (
    <>
      <title>Home</title>
      <meta name="description"
            content="Welcome" />
      <h1>Home</h1>
    </>
  );
}
Render title, meta and link tags anywhere in your tree — React automatically moves them into the document head. No third-party libraries needed.

Start with Native HTML

Controlled Inputs: React Owns the Value

Uncontrolled

function UncontrolledEmailInput() {
    return (
        <input
            type="email"
        />;
    )
}

The browser owns the input value.

Controlled

function ControlledEmailInput() {
    const [email, setEmail] = useState('');

    return (
        <input
            type="email"
            value={email}
            onChange={event => setEmail(event.target.value)}
        />;
    )
}

React supplies the value, and onChange updates the state that supplies it.

Choose controlled values when other UI or logic needs the current input. Use an uncontrolled input when React does not need to own its value.

Submit Buttons Trigger the Form's Submit Event

import { type SubmitEvent } from 'react';

function handleSubmit(event: SubmitEvent<HTMLFormElement>) {
    event.preventDefault();
}

function SignupForm() {
    return (
        <form onSubmit={handleSubmit}>
            <input type="email" name="email" />
            <button type="submit">Submit</button>
        </form>
    );
}
  • type="submit" triggers the form's onSubmit handler.
  • Pressing Enter in a form field also submits the form.
  • preventDefault() stops the browser's default page reload so React can handle the submission.

Per-Field Validation Part 1:
Composing Field Validators

Generic Functions

function validateNotBlank(value: string) {
    return value.trim() ? undefined : 'Required field'
}

function validateLength(value: string, minimum: number) {
    return value.length >= minimum
        ? undefined
        : `Use at least ${minimum} characters.`
}

function validateMatch(value: string, expected: string, message: string) {
    return value === expected ? undefined : message
}

These reusable helpers return a message or undefined.

Validators by Field

type SignupValidator = (values: SignupValues) => string | undefined

const validatorsByField: Record<SignupTextFieldName, SignupValidator[]> = {
    name: [(values) => validateNotBlank(values.name)],
    username: [(values) => validateNotBlank(values.username)],
    password: [
        (values) => validateNotBlank(values.password),
        (values) => validateLength(values.password, 8),
    ],
    passwordConfirmation: [
        (values) => validateNotBlank(values.passwordConfirmation),
        (values) => validateMatch(values.passwordConfirmation, values.password, 'Passwords do not match.'),
    ],
}

An object where each key is a field name, and each corresponding value is an ordered list of validators for that field.

Per-Field Validation Part 2:
How to Validate One Field

 // Run each of the field's validators, stop at the first message received
function validateField(fieldName, values) {
    for (const validatorFunction of validatorsByField[fieldName]) {
        const message = validatorFunction(values)
        if (message !== undefined) {
            return message
        }
    }
    return undefined
}

// Get one field's error (note: we will use a different strategy going forward)
const usernameError = validateField('username', values)

Collect Errors Across the Form

function validateForm(values: SignupValues): SignupErrors {
    const errors: SignupErrors = {}
    for (const fieldName of Object.keys(validatorsByField) as SignupTextFieldName[]) {
        const message = validateField(fieldName, values)
        if (message !== undefined) {
            errors[fieldName] = message
        }
    }
    if (!values.acceptedTerms) {
        errors.acceptedTerms = 'Accept the terms.'
    }
    return errors
}

Each field contributes at most one error; the outer loop continues after a field's chain stops. Submit can run every field's chain.

const [isSubmitted, setIsSubmitted] = useState(false)

When Should Submit Be Disabled?

<button
    type="submit"
    disabled={!isFormValid || isSubmitting}
>
    {isSubmitting ? 'Submitting…' : 'Submit'}
</button>

When the form is invalid

Useful when errors are already visible and update as the user edits.

Tradeoff: if errors appear only after submit, a disabled button blocks users from asking what needs fixing.

While a request is pending

Useful when repeating the action could create duplicate work; change the label to show progress.

Tradeoff: users must wait for the request to finish. The server still needs to handle duplicates safely.

If Submit is disabled, make the reason clear and the next step visible.

When Validation Needs the Server

The browser can check

Rules based on the current form values, such as required fields or a valid email format, can be checked immediately.

The server must check

Rules based on shared or changing information, such as whether a username is already in use, require a request to the server.

GET /availability?value=alex

HTTP 200 OK
{"valid":false,"message":"That value is already in use."}

A successful HTTP response can say a value is ineligible. A request failure is different: the client did not get an answer and cannot determine eligibility.

An availability check does not reserve a value. The server must check again when the value is submitted.

Async Validation Has a Lifecycle

  1. Not checked: there is no server answer for the current value.
  2. Checking: a request is in progress; the result is not known yet.
  3. Valid or invalid: the server answered and the UI can show its decision.
  4. Could not check: the request failed, so validity is unknown; allow a retry.

When the value changes, its previous answer no longer applies. A field can receive async request state as props to show loading feedback and, when appropriate, block edits while checking.

Submission Has Its Own States

When the user clicks Submit:

  1. Prevent browser reload.
  2. Check the current values' validity locally.
  3. If the values are invalid, show feedback and stop; no POST is sent.
  4. If they are valid, send the data with POST /{your_path} and show a pending state.
  5. While waiting, the outcome is unknown, so disable additional submits.
  6. When the server responds: confirm success or continue the workflow; on failure, explain the problem, keep the entered values, and allow correction or retry.

The browser can check the values entered; the server confirms rules that depend on shared or changing data.
